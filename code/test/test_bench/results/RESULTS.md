# Json_Rpc 性能压测结果

## 1. 测试环境

| 项目 | 值 |
| --- | --- |
| CPU | AMD EPYC 7K62（虚拟机，4 vCPU） |
| 内存 | 3.6 GiB |
| OS | Ubuntu 22.04.5 LTS |
| 编译器 | g++ 11.4.0 |
| 编译选项 | `-std=c++17 -O2 -g` |
| 网络 | 单机 loopback |
| 绑核 | 服务端 core 0，客户端 core 1-3 |

> 单机 loopback 下客户端与服务端抢同一台机器的 CPU，因此结果应视为**吞吐下界**，不是框架的理论上限。

## 2. 测试方法

新增 `code/test/test_bench/`：

- `bench_server`：RPC 服务端，提供 `Add`（零业务逻辑）、`Echo`（可变 payload）、`Stats`（返回累计 Add 次数）。
- `bench_client`：多线程同步压测客户端，统计 QPS、avg/p50/p90/p99/max、错误数；支持直连和注册中心发现。
- `bench_registry` / `bench_topic_server` / `bench_topic_client`：注册中心与发布订阅压测入口。
- `run_bench.sh`：一键执行 A/B/C/D 用例，输出 `results/*.csv`。

每个用例先 warm-up 100 次/线程，再统一释放屏障开始计时。参数使用唯一值并校验返回结果，错误数为 0 表示没有串包/错配。

复现：

```bash
cd code/test/test_bench
make clean && make
./run_bench.sh
```

## 4. 主要结论

1. **吞吐上限约 3.5 万 QPS（Add）**。1 线程 8.9k，4 线程 27.7k，8 线程 35.0k，16 线程 36.0k。8 线程后基本走平，服务端 CPU 已到 97%~98%，说明瓶颈是**服务端单 EventLoop 线程**，不是网络或客户端。
2. **延迟在饱和点仍然较低**。8 线程时 avg 0.224 ms、p99 0.473 ms；16 线程时 avg 0.434 ms、p99 0.811 ms。继续加并发只增加排队延迟，几乎不增加吞吐。
3. **单连接多路复用反而更快**。8 线程共享一条连接达到 41.4k QPS，高于 8 条连接的 37.2k QPS。说明在该并发下 `Requestor` 的全局锁不是瓶颈，减少连接/事件循环线程反而降低了调度开销。
4. **payload 影响明显**。1KB Echo 28.5k QPS，16KB Echo 降到 6.5k QPS，p99 从 0.48 ms 升到 1.93 ms。JSON 序列化/反序列化和数据拷贝是主要成本之一。
5. **服务发现在稳态下开销很小**。B1 33.4k QPS，与直连 8 线程的 35.0k 接近（差异在单机波动范围内），发现成本主要发生在首次调用。
6. **多 Provider 轮询分布准确**。B2 中两个 Provider 各承担 80,400 次请求，占比 **50.0% / 50.0%**（见 `probes.csv`），说明 `chooseHost()` 轮询和发现缓存工作正常。
7. **发布订阅**：发布 50,000 条耗时 7.592 s，发布侧 **6,586 QPS**；两个订阅者均收到 **50,000/50,000**，无丢失。注意 TopicServer 同样是单线程广播，订阅者越多，单条发布成本越高。
8. **短时稳定性**：D1 连续 40 万次请求无错误，QPS 32.6k；服务端 RSS 2.3 MB → 4.5 MB，文件描述符 8 → 8，没有 fd 泄漏。RSS 的小幅增长属于运行期缓冲/分配器行为，本次未做长时间验证。

## 5. 测试中发现的框架问题

1. **连接建立时序竞态（已修复）**：`MuduoClient::onConnection` 原来先 `_downlatch.countDown()` 再给 `_conn` 赋值（`code/common/net.hpp:389`）。`connect()` 被唤醒后若立刻发请求，可能拿到空的 `_conn` 导致空指针崩溃。压测客户端高并发建连时稳定复现。已把 `_conn` 赋值移到 `countDown()` 之前。
2. **同步调用无超时**：`Requestor::send` 里 `future.get()` 永久阻塞（`code/client/Requestor.hpp:68`）。服务端不响应时压测线程会挂死，脚本因此统一加了 `timeout`。
3. **无断线重连**：`Muduo TcpClient` 默认不重连，连接池里的失效 client 也不会因自身连接断开而被移除，后续调用存在空指针风险。
4. **每条消息构造 `random_device` + `mt19937`**（`code/common/details.hpp:63-91`）在压测热路径中会被计入开销，是后续可优化的点。
